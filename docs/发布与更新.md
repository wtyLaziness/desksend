# DeskSend 发布与更新

源码开发仓库为 https://github.com/wtyLaziness/desksend ，公开发布仓库为 https://github.com/wtyLaziness/desksend-releases 。两个仓库的 Releases 同步提供完整程序包、对应构建源码和校验文件。软件内置更新继续查询 desksend-releases。

产品版本在 `deskflow-master/cmake/DeskSendVersion.cmake` 中维护。主界面、托盘、关于窗口与 Windows 程序图标统一使用 DeskSend；底层核心、协议、配置和证书路径保留兼容名称。

## 更新流程

“帮助 → 检查 DeskSend 更新”查询公开仓库的最新正式 Release。已有自动检查偏好保留。客户端固定使用 DeskSend 发布源，不再读取旧配置中的 Deskflow 更新地址。

发布标签为 `v<版本>`，完整更新附件必须命名为 `DeskSend-<版本>-windows-x64.zip`。客户端要求附件已上传、下载地址属于指定仓库、大小大于零，且 GitHub 提供 SHA-256 digest。下载完成后再次核对大小和 SHA-256。

用户点击“安装并重启”后退出键鼠共享与界面；当前程序内置的更新脚本复核压缩包及包内文件清单，等待界面退出，并且只结束当前安装目录中的核心和传输组件。备份所有待覆盖程序文件后安装，始终保留整个 `settings` 目录。覆盖失败会尝试恢复备份并提示日志路径。备份保留在 `.desksend-backups`，更新日志保留在临时目录 `DeskSend-apply-*` 中。

自动覆盖仅支持可写目录中的便携版桌面模式；系统服务模式与安装版需要手动下载。GitHub 不可达时检查或下载会明确报错，不影响当前版本使用。首次发布 1.0.0 是新更新渠道的起点，旧版需要手动换用完整包。

## 构建与打包

1. 更新版本、提交代码，运行 `deskflow-win` 与 `localsend-cli-win`。两份产物必须来自同一个完整提交 SHA。
2. 下载两个 Actions 产物，使用 `scripts/package-release.py --deskflow-zip <ZIP> --localsend-exe <EXE> --build-commit <SHA> --out <新目录>` 组装完整包、对应源码和 `SHA256SUMS.txt`。脚本拒绝生产源码与构建提交不一致的情况。
3. 运行单元测试并在真实双机环境下核对跨屏拖拽、取消与更新流程；C++ 构建会运行包含发布元数据解析在内的单元测试。
4. 使用已登录的维护者 `gh release create` 将完整包、源码包及 SHA256SUMS 上传至公开仓库。先创建 draft，核对附件后发布。不在应用或仓库中存放 GitHub token。

`desksend-build.json` 记录版本、构建提交、源码提交及所有可覆盖文件的 SHA-256；默认配置不在覆盖清单中。源码包使用 `git archive`，不包含 `.git`、本机证书、运行配置和日志。
